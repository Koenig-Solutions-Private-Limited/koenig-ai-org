## Approach

**Chosen — three-layer defense in depth:**

1. **Backfill** `seo_description` (Content Author, one ticket per blog or one bulk ticket — Chief Content's call). Hand-written, 120–160 chars (target), answer-first, mirrors the H1 promise. Hard min 80 chars / hard max 160 chars (see Rejection Rules below).
2. **Prevent at G0** (Content Reviewer): add `seo_description` as a BLOCK-level item in the Structure dimension of `content-review`, using the Rejection Rules below.
3. **Catch at G5** (Publish Verifier): add check 11 — fetch live URL, extract `<meta name="description">`, assert it equals `seo_description` from vault and passes all Rejection Rules. Add a row to the SOUL.md output template.
4. **Belt-and-braces commit-msg hook** in `koenig-ai-org/.git/hooks/commit-msg` (installed via `scripts/install-hooks.sh`) that runs only when the diff touches `vault/blogs/*/draft.md`: if the new content sets `status: g0-passed` (or beyond) but the file fails any Rejection Rule, reject the commit with a clear, rule-specific message.

### Rejection Rules (applied identically by G0, G5, and the commit hook)

A description is **REJECTED** if ANY of the following are true:

1. **Missing/empty** — `seo_description` frontmatter key absent or empty string.
2. **Too short** — `length < 80` characters. **This rule fires regardless of content** — CEO's 2026-05-13 directive: short generic descriptions are rejected even when they don't look like commit messages. (Anything ≥80 and <120 PASSES the rule but the G0 review comment should *recommend* hitting 120+ for SERP truncation safety.)
3. **Too long** — `length > 160` characters. Google truncates around 155–160; over that is wasted budget.
4. **Commit-message pattern** — matches the regex below (case-insensitive at start-of-string):

   ```
   ^\s*(rev\s*\d+:|updated?\b|fixed?\b|standardized\b|bumped\b|refactored\b|chore\b|wip\b|added?\b|removed\b|merged?\b)
   ```

   These openers signal an internal `whats_new` rev note leaked through the fallback chain. **The length rule (rule 2) catches everything; this rule is a fast, specific diagnostic for the most common failure shape.**

The rules are checked in order; the rejection message names the first rule that fired. Rule 2 is the safety net for *generic* short descriptions that wouldn't trip rule 4 (e.g. a 50-char author-written blurb that happens to start with a noun). Rule 4 stays in the spec to give clearer error messages for the well-known leak.

### Regression fixture

`/blog/2026-04-30-anthropic-creative-connectors` — live meta description as of 2026-05-13T03:02Z is `"Updated Resolume and Blender descriptions for accuracy"` (54 chars). Used as a **named fixture** in tests:

- **Length-rule fixture:** 54 chars → MUST be rejected by rule 2.
- **Rendered-meta fixture:** the G5 check-11 implementation MUST be exercised against this URL during PR review; output MUST be `❌ G5 BLOCK` until the backfill child ticket lands a proper `seo_description` for this slug.
- **Plan-review gate:** if a reviewer reads a future revision of this plan and finds it only catches rule 4 (commit-message patterns) and not rule 2 (length floor), the plan should be rejected as a regression of CEO's L3 directive.

**Rejected alternatives:**

- *Just backfill; rely on existing gates.* — Rejected: G0 today never checked `seo_description`. Without G0+G5 hardening the same bug recurs the next time someone forgets the field.
- *Move the field into the body + auto-extract first paragraph.* — Rejected: SEO descriptions are a deliberate marketing artifact (CTR-tuned, answer-first); auto-extracted lede paragraphs are usually too long, miss the keyword promise, and lose the conversion verb. Hand-write them.
- *Make `seo_description` required at the TypeScript layer (drop the fallback in `page.tsx`).* — Rejected as the only fix because builds would simply fail silently per-route. Keep a *safe* fallback (e.g. site tagline), but make G0 + commit hook the actual enforcement so we never ship a fallback to a live URL.
