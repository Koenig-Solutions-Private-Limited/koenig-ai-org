## Approach (1 chosen, 2 rejected)

**Chosen: Skill-encoded sandboxed-attempt + sub-ticket dispatch.**
Write `runnable-code-check` as a deterministic, scripted recipe that any reviewer (Code Reviewer today, QA tomorrow) invokes against a markdown path. It does four things:
1. **Extract.** Pull every fenced block tagged `bash|sh|shell|python|py|typescript|ts|javascript|js`, skipping blocks immediately preceded by `<!-- runnable-check:skip -->`. Capture `block_index`, `lang`, `start_line`, `end_line`.
2. **Pre-flight (cheap).** Syntax-check via `bash -n` / `python3 -m py_compile` / `node --check` / `tsc --noEmit --target es2022 --strict` (TS only if `tsc` is on PATH). A pre-flight FAIL short-circuits to `FAIL-syntax` and the runtime attempt is skipped.
3. **Placeholder substitution.** Build a per-block env dict where any `$VAR` or `${VAR}` referenced inside the block gets a safe default (rules above). Write the substituted block to `$(mktemp -d)/block.<ext>`.
4. **Sandboxed run.** Invoke `timeout 30 codex sandbox linux -- <interpreter> $tmpdir/block.<ext>` with a clean environment that has only the substituted placeholders. Classify the exit:
   - `0` → `PASS`
   - non-zero **and** stderr matches `Could not resolve host|Connection refused|Network is unreachable|Temporary failure in name resolution` → `SKIP-network` (still counted as PASS upstream)
   - non-zero **and** block references a literal placeholder still left ungrounded (`<your-…>` survived substitution) → `SKIP-env` (PASS upstream)
   - non-zero with timeout → `FAIL-timeout` (BLOCK upstream)
   - non-zero otherwise → `FAIL-runtime` (BLOCK upstream) with first 40 lines of stderr inlined.
5. Return a structured table: `block_index | lang | lines | preflight | runtime | classification | reason`.

Content Reviewer's G0 scan adds a single grep for ```` ```(bash|sh|python|py|typescript|ts|javascript|js) ````. If any matches, it creates **one sub-ticket per draft** (not per block) with title `[Content] runnable-code-check: <slug>`, body = absolute path to the markdown, `parentId = current ticket`, `assigneeAgentId = 3e4cd715-…` (Code Reviewer), kind label `content-code-sample`. Content Reviewer flips the parent to `blocked` with `blockedByIssueIds: [sub-ticket-id]`. When the sub-ticket returns `done` with a PASS comment, the parent unblocks and G0 proceeds. Any `FAIL-*` row in the table forces G0 to BLOCK with the table inlined.

**Rejected — Static syntax-only checks.** Cheaper and deterministic, but the parent DoD explicitly demands a runtime attempt ("try to run in a sandboxed worker"). Syntax-only ships a check that says nothing about whether the sample actually executes. Rev 1 of this plan made this mistake; rev 2 corrects it.

**Rejected — Reviewer-inline checking, no sub-ticket.** Content Reviewer could just run the skill itself. Faster (no extra ticket), but breaks the "Reviewer is a Sonnet/Opus editor, not a code engine" lane, hides the audit trail, and concentrates sandbox blast-radius on the editor agent. The parent-issue description explicitly asks for a Code Reviewer sub-ticket; the separation is the point.

## Risk

- **Sandbox tool drift.** If `codex sandbox linux` is missing on the Code Reviewer's runtime (e.g., a future Codex upgrade renames or removes the subcommand), the skill must fail loud rather than silently fall back to unsandboxed execution. Mitigation: the skill begins with a `command -v codex && codex sandbox --help | grep -q "linux"` precheck. If the check fails, the skill returns `FAIL-sandbox-missing` for every block and escalates the sub-ticket to Chief Engineering instead of running anything unsandboxed.
- **`shellcheck`/`tsc` availability.** Best-effort. `bash -n` and `node --check` are always available baselines; `shellcheck` is enabled when `command -v shellcheck` is non-empty, and `tsc` likewise. A missing optional tool yields `preflight=SKIP-no-<tool>` rather than blocking.
- **Long-tail interpreters in the wild.** A draft may use `python` (not `python3`) or `ts-node` (not `tsc`). The skill maps known aliases up front; an unrecognized fence (e.g., ```` ```go ````) is silently skipped — out of scope for V1.
- **Substituted-env false PASS.** A block that *would* fail with a real secret could accidentally pass with `stub-key` if the failure path is gated on a real API response. Acceptable for V1 — the parent ticket says "try to run", not "prove production-correct"; surfacing syntactic + reachable-codepath validity already catches the common breakage (typos, missing args, indentation, dangling pipes).

## Out of scope

- Auto-fixing broken samples — Code Reviewer reports; Content Author fixes.
- Languages beyond bash/python/typescript/javascript (no SQL, no Go, no Rust). The four chosen cover ~95% of current vault content per a spot-grep of `vault/blogs/`.
- Triggering the check on `vault/courses/**` chapters in V1 — same logic should work but the rollout is intentionally blog-only until we have one clean smoke-test cycle.
- Allowing sandbox network egress (e.g., to actually hit `api.openai.com`). Permanent no — secrets and rate-limits would have to be solved first. `SKIP-network` is the correct V1 behaviour.
- Mocking external APIs inside the sandbox to coax a real `PASS` out of network-bound blocks. Tracked as a follow-up if `SKIP-network` rates become noisy.
- Running blocks on `vault/courses/**` chapters — V1 is blog-only (see above).
