# Plan: unstick KOEA-10/KOEA-488 + close the approved→publish gap on the CEO seat

## Problem statement

Two issues sit at `status=in_review` despite having **approved** `request_board_approval` rows in the DB:

| Key       | Approval ID              | Approved at          | Type | Slug                                          |
|-----------|--------------------------|----------------------|------|-----------------------------------------------|
| KOEA-10   | `8333ee51-4f1e-42df…`    | 2026-05-01T11:28:10Z | blog | `2026-04-30-anthropic-creative-connectors`    |
| KOEA-488  | `88ede706-3748-4354…`    | 2026-05-12T09:28:29Z | blog | `gpt-5-5-vs-claude-opus-4-7-agentic-coding`   |

Both issues have empty `metadata` (no `publish_state`, no `slug`), so they are invisible to `scripts/publish-action.sh` (which keys on `status=done AND metadata.publish_state=g4-approved`).

## Root cause (verified end-to-end)

1. **`/api/approvals/:id/approve` route** (`server/src/routes/approvals.ts:136-230`) handles the approve flip correctly:
   - Persists the approval state via `approvalService.approve(...)`.
   - When `applied===true`, posts a `heartbeat.wakeup()` to `approval.requestedByAgentId` with `reason: "approval_approved"` and a context snapshot carrying `approvalId, issueId, issueIds, wakeReason: "approval_approved"` (lines 167-188).
   - **Critically, the route does NOT mutate any linked issue** — that is left to the requesting agent.

2. **The requesting agent for both approvals is the CEO** (`5a1e1c39-1ba7-46af-a4df-c6bbef8549e9`). The `g4-routing` SKILL the CEO ran when *creating* the approval defines a correct post-approval branch (`companies/learnova-academy/skills/g4-routing/SKILL.md:59-63`):
   > On APPROVE: PATCH `metadata.publish_state="g4-approved"` (status stays `done`).

3. **But the CEO has no heartbeat path that re-enters `g4-routing` on `wakeReason=approval_approved`.** A grep across `companies/learnova-academy` for `approval_approved`, `approval\.approved`, or `wakeReason.*approval` returns zero matches. The CEO's SOUL preamble (`companies/learnova-academy/agents/ceo/SOUL.md:148-156`) only special-cases `issue_commented`; any other wakeReason falls into the default heartbeat loop, which runs daily-triage / EOD / G3 review — never the "an approval I requested just landed" branch. The wakeup is consumed silently.

4. **Result**: every approved `request_board_approval` row is stranded unless the CEO happens to re-run `g4-routing` on the same ticket out-of-band. Comments on both stuck issues confirm the CEO posted "G4 routed" before approval and never posted "G4 approved → publishing" after. This is a **structural**, repeating bug — not a one-off race.

5. **Cross-check with the upstream gap (KOEA-1137):** even if this plan flips `publish_state=g4-approved`, the dispatcher (`scripts/publish-action.sh`) is still broken (launchd unloaded, missing `GH_PAT_DISPATCH`, no auth header, wrong `COMPANY_ID`). KOEA-1137 fixes that and is independent of this plan. The two plans compose: KOEA-1199 unblocks `in_review → g4-approved`; KOEA-1137 unblocks `g4-approved → published`.

## Why not fix the server route directly

`CLAUDE.md` (project root) declares `server/`, `packages/`, `cli/`, `ui/` as upstream paths to leave alone. The fix must live in `companies/learnova-academy/` (our customizations) and/or `scripts/`. We do not modify `server/src/routes/approvals.ts` even though that would be the structurally cleanest place.

## Approach (chosen)

**Two-pronged, both in our fork-owned tree:**

A. **One-shot recovery script** (`scripts/recover-stuck-approvals.sh`) that takes approval IDs, fetches each, resolves linked issues, and PATCHes the right metadata + status — used immediately for the two stuck approvals and retained for future stragglers.

B. **CEO post-approval handler skill** (`companies/learnova-academy/agents/ceo/skills/on-approval-approved/SKILL.md`) + a SOUL preamble entry that routes `wakeReason=approval_approved` to it. Pure markdown — the CEO is a `claude_local` agent and reads its skill pack each heartbeat, so no rebuild is required.

The script handles past stragglers; the skill prevents future ones. Neither touches upstream code, server routes, or Convex.

## Approaches rejected

- **Modify `server/src/routes/approvals.ts` to PATCH linked issues on approve** — cleanest, deterministic, but violates the "don't touch upstream" rule in CLAUDE.md. Defer to an upstream Paperclip PR if the pattern recurs across companies.
- **Add a launchd poller that scans `issue_approvals` for approved rows whose linked issues are still `in_review`** — band-aid for the same structural gap; duplicates state-machine logic; reintroduces the same launchd-loading failure mode that bit KOEA-1137. Skip.
- **Auto-close blogs at G3 PASS (enforce `blog-skip-g4` in code)** — addresses a *different* bug (blogs entering G4 at all); both KOEA-10 (2026-05-01, same-day-as-policy) and KOEA-488 (2026-05-11, ten days after policy lock) suggest g3-alignment is still routing blogs to G4. **Out of scope** for KOEA-1199; flag as a separate follow-up ticket.

## Per-ticket recovery disposition

Both blogs were routed to G4 against the `blog-skip-g4` policy. Since Vardaan did in fact approve them, the operationally correct recovery is "publish them," not "revoke the approval." But KOEA-10 already has a sibling publish ticket and KOEA-488 does not:

| Ticket   | Sibling publish ticket?                       | Recovery                                                                            |
|----------|-----------------------------------------------|-------------------------------------------------------------------------------------|
| KOEA-10  | **Yes** — KOEA-352 (Cohort A in KOEA-1137 plan, `publish_state=g4-approved`, slug=`2026-04-30-anthropic-creative-connectors`). | Close KOEA-10 as `status=done`, leave `metadata.publish_state` unset. KOEA-352 owns the deploy via publish-action.sh once KOEA-1137 lands. |
| KOEA-488 | **No** — verified by searching company issues for the slug. KOEA-488 IS the publish ticket. | PATCH `status=done`, `metadata.publish_state=g4-approved`, `metadata.slug=gpt-5-5-vs-claude-opus-4-7-agentic-coding`. publish-action.sh will pick it up after KOEA-1137 lands. |

Both dispositions are idempotent and reversible (revert via a single PATCH).

## Steps (Executor follows in order)

1. **Author `scripts/recover-stuck-approvals.sh`** (`bash`, idempotent, supports `--dry-run` and `--apply`). Behaviour:
   - Reads `PAPERCLIP_API_URL`, `PAPERCLIP_API_KEY` (or `PAPERCLIP_BOARD_TOKEN`), `PAPERCLIP_COMPANY_ID` from env (fall back to `.env.koenig`).
   - Accepts one or more approval IDs as args.
   - For each: `GET /api/approvals/{id}` → require `status=approved` and `type=request_board_approval`; `GET /api/approvals/{id}/issues` → for each linked issue, fetch current state; classify per disposition table (look up `metadata.slug`, look for sibling publish ticket by slug, decide PATCH payload).
   - Print proposed PATCH per issue; in `--apply` mode, issue `PATCH /api/issues/{id}` with the payload. Add an `Idempotency-Key` header derived from `recover-stuck:{approvalId}:{issueId}`.
   - After each successful PATCH, POST a comment on the issue: `Recovery: KOEA-1199 — approved approval {id} stranded; status flipped to done. publish_state={…|null}.`
   - Log to `~/.paperclip/logs/recover-stuck-approvals.log`.

2. **Dry-run + apply for the two known approvals**:
   ```bash
   bash scripts/recover-stuck-approvals.sh \
       8333ee51-4f1e-42df-82ea-09f2cb380e90 \
       88ede706-3748-4354-8194-24892f84d2c8 --dry-run
   # confirm output matches the disposition table, then:
   bash scripts/recover-stuck-approvals.sh \
       8333ee51-4f1e-42df-82ea-09f2cb380e90 \
       88ede706-3748-4354-8194-24892f84d2c8 --apply
   ```

3. **Add `companies/learnova-academy/agents/ceo/skills/on-approval-approved/SKILL.md`** with this procedure (mirror existing skill format — frontmatter `schema: agentcompanies/v1, kind: skill, slug: on-approval-approved`):
   - **Trigger**: heartbeat where `wakeReason === 'approval_approved'`.
   - **Inputs (from `contextSnapshot`)**: `approvalId`, `issueId`, `issueIds`, `approvalStatus`.
   - **Procedure**:
     1. `GET /api/approvals/{approvalId}` — verify `status=approved` (guard against stale wakes); abort silently otherwise.
     2. For each linked issue in `issueIds`:
        - `GET /api/issues/{id}` — read current `status`, `metadata.publish_state`, `metadata.slug`, `metadata.content_type`.
        - **Idempotency guard**: if `status !== 'in_review'` OR `metadata.publish_state` is already set, skip + comment `on-approval-approved: already actioned (status={status}, publish_state={publish_state}); no-op.`
        - Otherwise PATCH per the disposition rule (same logic the recovery script uses): if a sibling publish ticket exists for the same slug with `publish_state=g4-approved`, close as `status=done` with no `publish_state`; else set `status=done` + `metadata.publish_state=g4-approved` + carry `metadata.slug` if present.
     3. Post a single CEO comment on the issue: `✅ G4 approved → publish_state=g4-approved (or status=done deferring to {sibling}). Publish-action will dispatch in ≤60s.`
     4. Append a one-line entry to today's EOD draft at `vault/retrospectives/ceo/<date>-eod-draft.md` (create if absent).
   - **Never do**: re-fire on a stale (`status != approved`) approval; PATCH if `status !== in_review`; mutate any other issue; create children.
   - **Budget**: ≤$0.05 per invocation (one GET + small PATCH).

4. **Update CEO SOUL preamble** (`companies/learnova-academy/agents/ceo/SOUL.md`, immediately above the "Comment-trigger throttle" section at line 148): add a new short section "Approval-completion priority":

   - Roll back the test ticket via a single PATCH back to `in_review`.

## Risk

- **Idempotency hazard on the CEO skill**: if the heartbeat is fired twice for the same approval (e.g., approvals.ts retry, or executor re-runs the script in parallel), the skill could PATCH twice. **Mitigation**: skill's step 3.2 guard short-circuits if `status !== 'in_review'`, and the recovery script uses an `Idempotency-Key` header. Both are no-ops on second hit.
- **Wrong sibling-publish-ticket lookup**: if the script's slug search returns a false positive, KOEA-488 could be closed as "deferred to sibling" and never publish. **Mitigation**: dry-run is mandatory before `--apply`; the Executor reviews the disposition; the lookup uses an exact-match on `metadata.slug`, not title fuzzy-match.
- **CEO skill bloat**: adding another always-on heartbeat branch slightly raises CEO token cost per wake. **Mitigation**: the skill exits early when `wakeReason !== 'approval_approved'`, and the wake is rare (≤1/day at current volume).

## Rollback

- **Recovery script effects**: each PATCH is reversed with `PATCH /api/issues/{id}` setting `status=in_review`, clearing `publish_state` and `slug` if added. The script's log captures pre-PATCH state for the Executor to copy back. No vault mutations.
- **CEO skill / SOUL**: revert the commit on the PR branch; the CEO will fall back to the pre-fix behaviour (silent strand) at next heartbeat.
- **No upstream / server / DB changes** to undo.
