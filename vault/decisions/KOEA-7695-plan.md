# Plan: Add Related Courses links to /learn/[slug]

## Goal

Every `/learn/[slug]` course page should SSR-render a `Related courses` section near the bottom of the page, before site footer chrome, with at least three links to other `/learn/<slug>` course routes. Success is observable in static HTML: Google's crawler can see the H2, the anchors, the course titles, and one-line descriptions without client-side JavaScript.

## Context

- Files to read first:
  - `learnovaBeast/learnova-academy/src/app/(site)/learn/[slug]/page.tsx:51-61` - route is static and generates one page per discoverable course.
  - `learnovaBeast/learnova-academy/src/app/(site)/learn/[slug]/page.tsx:92-108` - existing course description helper and `getCourse` lookup.
  - `learnovaBeast/learnova-academy/src/app/(site)/learn/[slug]/page.tsx:340-350` - bottom of hero/course-progress area and start of chapter content.
  - `learnovaBeast/learnova-academy/src/lib/courses.ts:114-130` - course metadata available for related card display.
  - `learnovaBeast/learnova-academy/src/lib/courses.ts:425-483` - vault-backed course loader and `listDiscoverableCourses`.
  - `learnovaBeast/learnova-academy/package.json:1-31` - script-based verification, no Vitest setup.
- Relevant prior work: KOEA-43 identified the missing course cross-links; KOEA-7695 narrows the remaining work to `/learn/[slug]` only. Chief Engineering resolved planner-chain approval `5ee71473-b59d-47c1-a027-c87d57bfaea7` and authorized this chain as intentional Plan-Review -> Implement -> G_code -> QA pipeline work.
- Constraints:
  - Work only in `learnovaBeast/learnova-academy` on a feature branch based on `academy/redesign-v1`.
  - Do not touch other portals, blog link fixes, meta descriptions, deployment workflows, or recommendation infrastructure.
  - Current vault has 22 discoverable course outlines; the implementation must cover every current slug, including outline-draft courses generated by `listDiscoverableCourses`.
  - Keep the implementation to no more than five files and about 300 LOC so this remains a single execution ticket.

## Approach (1 chosen, alternatives rejected)

**Chosen**: Add a complete static slug mapping in `src/data/related-courses.json`, a small `src/lib/related-courses.ts` helper that resolves those slugs to existing `Course` metadata, and a server-rendered section inside the existing `/learn/[slug]` page. This is deterministic, easy to review, uses the same vault-backed course data the page already reads, and lets a Node verifier prove every current course has at least three valid non-self targets.

**Rejected**: Runtime keyword-overlap scoring only - it is simple, but it makes link choices harder to audit and can produce surprising SEO links when course titles change. **Rejected**: Add related-course frontmatter into every vault course outline - this would touch 22 content files and exceed the ticket scope. **Rejected**: Client-side related links in `client-shell.tsx` - it would miss the SSR/indexability requirement.

## Steps (Executor follows in order)

1. Create `learnova-academy/src/data/related-courses.json` with one key per current `vault/courses/*/outline.md` slug and at least three existing non-self related slugs per key. Seed the five KOEA-7695 suggested mappings first, correcting stale names such as `mcp-from-first-principles` to `mcp-from-first-principles-to-production`, then fill the remaining current slugs by vendor/topic family.
2. Add `learnova-academy/src/lib/related-courses.ts` that imports the JSON map, accepts the current `Course` plus `listDiscoverableCourses()` results, drops missing/self/duplicate targets, and returns exactly three related courses with `{ slug, title, description }`. Derive description from `learning_outcomes[0]`, else `target_audience`, else the same level/vendor fallback shape used by `courseDescription`.
3. Update `learnova-academy/src/app/(site)/learn/[slug]/page.tsx` to compute `const allCourses = listDiscoverableCourses()` once per render, use it for related resolution, and render a `<section aria-labelledby="related-courses-heading">` with H2 text exactly `Related courses`, three card-style `Link` anchors to `/learn/${related.slug}`, title, and one-line description. Place it after the chapter/certificate block and before `</main>` so it is above footer chrome and SSR-rendered.
4. Add `learnova-academy/scripts/verify-related-courses.mjs` that reads `src/data/related-courses.json` plus `KOENIG_VAULT_ROOT/courses`, validates every discoverable course has a mapping, each mapping has at least three unique existing target slugs, and no target equals the source slug.
5. Add a package script such as `"verify:related-courses": "node ./scripts/verify-related-courses.mjs"` and include it in the implementation verification notes. Do not replace existing `test`, `typecheck`, or build scripts.
6. Run targeted verification from `learnova-academy`: `pnpm verify:related-courses`, `pnpm typecheck`, and `pnpm build`. If the implementation environment has a running preview server, also curl or view at least `claude-tool-use-from-zero`, `mcp-from-first-principles-to-production`, and one non-AI-marketing course to confirm the raw HTML contains the section and three `/learn/` anchors.

## Risk

- Static mappings can drift when new courses are added. Mitigation: make `verify:related-courses` fail when a discoverable course lacks a mapping or points at a missing slug, forcing future course additions to update the SEO links intentionally.

## Out of scope
